## 问题 2：stride 候选枚举

自动枚举（`stride_candidates`）：

```python
cands = [s for s in range(stride_min, window + 1) if window % s == 0]   # window 的约数
cands = sorted(set(cands), reverse=True)                                # 降序 = 由贵到便宜
return cands if cands else [window]                                     # 兜底：朴素
```

- 取约数是为了保证窗口对齐（否则最后一个窗口长度不规则，会引入尾部偏差）；
- 包含 `window` 自身 = 朴素评测（cost 1x），保证"退化路径一定在候选里"；
- 空候选兜底为 `[window]`。

手填候选（`KNEE_CANDIDATES`，v4 新增的边界处理）：

```python
_parse_knee_candidates(raw, window, stride_min)
  - 非整数字面量  -> int() 抛 ValueError（参数写错应当 fail fast，不静默吞掉）
  - 0 / 负数      -> 过滤（0 会在 cost = window/s 处除零）
  - > window      -> 过滤
  - 过滤后为空    -> 回退自动枚举（绝不把空列表交给 pick_stride_by_knee）
```

**v4 修掉的两个真 bug**（都有反向验证，见下）：

1. 旧版过滤条件只写了 `if int(s) <= window`，**0 和负数会放行**。实测：
   `KNEE_CANDIDATES="0,-1,9999"` 时旧实现直接 `ZeroDivisionError: division by zero`（真崩溃，非假想）。
2. 旧版在全部非法时得到 `[-1, 0]`（非空），交给 `pick_stride_by_knee` 后崩溃。

**预算分支的第二个真 bug**（同样有反向验证）：

旧版 `pick_stride_by_knee` 的 else 分支（预算连 1x 都付不起）返回 `rows[-1]`，
而 `rows` 是降序，`rows[-1]` 是 **stride 最小 = 代价最大** 的候选——与注释写的"退化为朴素"
正好相反，且直接突破 `EVAL_COST_BUDGET`。实测：`EVAL_COST_BUDGET=0.25` 时旧实现
选出 `stride=32, cost=8.0`（预算的 32 倍）。

v4 改为：真正退化为朴素（`stride=window, cost=1x`），并在 `info["budget_ok"]=False`
里显式暴露，调用方打 WARN 日志。

反向验证脚本（证明这些用例**真的能抓到**旧 bug，而不是恒真空转）：

```
python evidence/回归测试_反向验证.py        # 输出留档 evidence/回归测试_反向验证_输出.txt
```

输出要点：4 条用例，新实现 PASS、旧实现 FAIL，其中两条给出了具体的失败数值
（`cost=8.0` 突破预算、`ZeroDivisionError`）。**4/4 能区分新旧实现。**

## 问题 3：`EVAL_COST_BUDGET` 的口径

定义：**愿意为最终评测多付的前向 token 倍数**，相对于官方朴素评测。

- 朴素评测：验证集切成互不重叠的 `train_seq_len` 窗口，**每个验证 token 恰好前向一次** → 1x。
- 滑窗评测：窗口步长 `stride`，窗口数 ≈ `total_tokens / stride`，每个窗口前向 `seq_len` 个 token
  （含 padding），但只计分尾部 `stride` 个 → 摊销代价
  `C(S) ≈ (total_tokens/stride × seq_len) / total_tokens = seq_len / stride`。

代码里 `pick_stride_by_knee` 用的正是 `cost = window / s`，与上式一致。

**v4 新增：真实口径的运行时审计。** 旧版 docstring 声称审计 forward token 数，
实际累计的是**计分** token 数（等于验证集大小，恒等于 1x，等于没审计）。
现在 `eval_val_sliding` 里新增：

```python
forward_tokens = torch.zeros((), device=device, dtype=torch.float64)
...
forward_tokens += float(bsz * seq_len)      # 真实前向 token 数（含 padding）
...
dist.all_reduce(forward_tokens, op=dist.ReduceOp.SUM)
...
print(f"sliding_eval_cost forward_tokens={fwd:.0f} scored_tokens={scored:.0f} "
      f"amortized_cost={fwd / max(scored, 1.0):.3f}x   # 1x = 官方朴素评测")
```

于是 `EVAL_COST_BUDGET` 的口径在真机日志里**可直接核对**（预测值 `window/stride`
vs 实测 `amortized_cost`），口径不再是纸面约定。

诚实限定：padding 会计入 `forward_tokens`（第 5 个改动块之前的窗口构造不变），
因此 `amortized_cost` 在验证集尾部会略高于 `window/stride`。这是刻意的——
它反映真实算力消耗。

## 问题 4：`forward_logits` 是否真的产出逐位置 logits

验证脚本：

```
python evidence/forward_logits_等价性验证.py   # 输出留档 evidence/forward_logits_等价性验证_输出.txt
```

三条断言，`tie_embeddings=True/False` 各跑一遍：

1. **形状**：`(bsz, seq_len, vocab)` —— 未池化；
2. **数值**：用它重算的 `cross_entropy` 均值与官方 `forward()` 的损失 `|Δ|max = 0.000e+00`；
3. **因果**：改 `x[0, j]` 只影响位置 `j` 及其之后，位置 `< j` 完全不变
   （实测 4 个位置，前序位置最大变化 `0.00e+00`）——这是按位置切分
   `s = max(wlen - stride, 0)` 能成立的前提。

**过程中踩到的坑（一并留档，因为它会让检验变成恒真空转）**：
baseline 的 `CausalSelfAttention` 有 `self.proj._zero_init = True`，`lm_head` 也初始化为全零。
所以在**未训练的初始点**上：

- `tie=False`：logits 恒为 0，改任何输入 token 输出都不动 → 检验**假阴性**；
- `tie=True`：因 proj 零初始化，位置之间没有耦合，改 `x[0,8]` 只有位置 8 自己变
  → 「逐位置/因果」检验**平凡成立**，测等于没测。

我在第一版脚本里就踩了这个坑（脚本报 FAIL 才发现的）。现在的版本先对全部参数做一次
非零随机初始化再测，并把退化现象作为 `[0]` 对照段打印出来。

另外：`forward_logits` 与 root baseline 的 `forward` 是**镜像**关系（中间代码逐字相同，
只在末尾 `return` 处分叉：一个返回 `cross_entropy` 均值，一个返回 `view(bsz, seq, vocab)`），
且 root baseline 里 `forward` 本身与官方逐字节一致。
