## 为什么可以合法地把官方代码放进自己的交付包

- 上游许可：`evidence/upstream/LICENSE_upstream.txt` = **MIT License, Copyright (c) 2026 OpenAI**。
  MIT 允许再分发，条件是保留版权声明——这里原样保留了 LICENSE 与 `THIRD_PARTY_NOTICES.md`。
- 放进来的是**评审要核对的那个基线**，不是我们的成果：本方案的全部改动都
  在 `evidence/submission_script.patch` 里（+349 / -12 行，5 个块）。
- 归因在 `卢怡然_C2G_submission.json` 的 `attribution` 字段与 README 里都写明了。

## 基线到底是哪一个（这一步很关键，v3 没讲清楚）

上游仓库里有多个 `train_gpt.py`，选错了整个 diff 就没意义。本方案的基线是
**仓库根目录的 `train_gpt.py`**（1126 行，sha256 `c6cae5e7…`），不是排行榜记录里的那些。

判定依据（不是靠猜文件名，是靠结构）：

| 文件 | 行数 | 模型结构 | 与本提交脚本的关系 |
|---|---|---|---|
| `train_gpt.py`（根） | 1126 | 简单 encoder/decoder + skip_weights | **是基线**。提交脚本的 `forward` 与它逐字节相同 |
| `records/…/2026-03-19_SlidingWindowEval/train_gpt.py` | 1366 | 含 `num_loops` / `lora_adapters` / `num_unique_layers` | **不是基线**。架构不同。只借鉴它的滑窗**机制** |
| `records/…/2026-03-17_NaiveBaseline/train_gpt.py` | 1126 | 同根 | 三方对照用 |

程序化确认：把提交脚本里的 `GPT.forward` 源码与两份候选分别比对，只有 root 版
逐字节相同；把 `eval_val_sliding` 与 1366 行记录版比对，只有 13 处差异（且全是注释/
审计日志/变量名，计分核心一行未动）。复现命令见 `代码自查_评审五问.md`。

## 拿到包以后怎么核对（三条命令）

```bash
# 1. 基线 + 补丁 -> 提交脚本，应当与包里的文件字节一致
git -c core.autocrlf=false apply -p1 evidence/submission_script.patch
sha256sum 卢怡然_C2G_train_gpt.py        # 应等于 base_sha256.txt [2] 里的值

# 2. 重新算一遍所有哈希（含补丁可 apply 性自检）
python pg_lab/hash_registry.py

# 3. 单元测试 + 反向验证（证明新加的回归用例真能抓到旧 bug）
python pg_lab/selftest.py                # 12/12
python evidence/回归测试_反向验证.py      # 4/4 能区分新旧实现
```

## 诚实清单

- 基线是**本机已有的上游克隆**复制来的，不是这次联网重新下载的（本机无外网）。
  因此只能保证它与本机那份克隆逐字节一致（生成时会断言两份一致，见
  `pg_lab/build_submission.py` 的 `_resolve_base()`），**不能**保证它等于 GitHub 上
  此刻的最新版——上游仓库在比赛期间是持续更新的。
- 如果评审拿到的上游 `main` 与这里登记的根基线 sha256 不同，请以上游当时的
  commit 为准；本提交脚本对应的基线就是 sha256 `c6cae5e7…` 这一版。
